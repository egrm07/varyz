---
name: varyz-cloud-activate
description: Help an existing Varyz Cloud subscriber connect local Varyz, explicitly choose confirmed preferences to sync, verify hosted retrieval, and check a supported phone tool.
---

Use only after the user requests connection or activation of an existing account. This is account setup, not a sales prompt. Never initiate checkout, manufacture a payment success, or treat installation, purchase, or sign-in as permission to upload.

1. Confirm the service is live at the user's approved HTTPS origin. The planned cloud.varyzai.com address is a placeholder until launch. If unavailable, say so and continue using local Varyz. Never substitute another service or collect a password/token in chat.
2. Run `varyz cloud connect --url <approved live origin> --config <local config>` after sign-in authorization. The browser handles credentials. Then run `varyz cloud status` with the same config. Verify active entitlement from the server; a browser checkout return or user screenshot cannot grant access. Inactive access receives a neutral account-status explanation, with no purchase or upgrade link.
3. Explain the choice simply: "Which projects' rules and preferences should sync? Your global rules are included. New confirmed rules in those projects will sync too." Only confirmed rules, explicitly answered preferences and stated workflows are eligible. Files, messages and the indexed archive stay local. Do not invent per-rule selection: the current controls choose project scopes plus global knowledge, or all confirmed knowledge.
4. After explicit scope authorization, run `varyz cloud select --all-confirmed --project <chosen project>` (repeat projects), or omit `--project` only if the user explicitly chose all scopes. Always pass the intended config. Selection sends nothing. Existing synced scopes cannot silently change: report any error and explain that existing Cloud data remains; do not disconnect or delete as a workaround.
5. Run `varyz cloud sync --dry-run`. Show the upload and deletion counts, then get explicit authorization to send the selected projection. Counts do not reveal the exact text: if the user wants to review it, show eligible local rules/preferences privately before approval. If deletions appear, explain them too. Never use an automatic yes, resolve conflicts, widen scopes or send archive text as a shortcut.
6. Run `varyz cloud sync` once authorized. A conflict requires the user's choice; don't automatically use `--accept-remote` or `--keep-local`. On failure, report the actual failure and keep local use available.
7. Choose one existing confirmed selected rule that applies to the project (use local rules list; never create a synthetic preference). Run `varyz cloud verify --rule-id <id> --project <project>` with the same config. This checks paid account binding and actual hosted `start_task` retrieval. Success proves server retrieval only, not phone support.
8. Ask the user to open an actually supported phone AI tool, connect the same Varyz account through its available connection UI, and request a real task using that project's rules. Read the tool schema and use hosted `start_task` for that project. Compare the actual returned selected rule; do not infer success from model wording or local verification. A published plugin/phone connection may not yet exist: state that limitation, never invent a store link. Mark phone activation complete only after this real-device check succeeds.

If the user declines syncing, stop. `varyz cloud disconnect` turns syncing off and revokes local credentials; existing Cloud data remains. Account deletion and exports are separate explicit requests. Do not save activation state as a user preference or use it to target promotions.
