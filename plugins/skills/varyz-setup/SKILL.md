---
name: varyz-setup
description: Install or repair the optional local Varyz companion after the user requests setup, review selected sources and agent connections, and retrieve a first useful source-backed result.
---

Use this skill when the owner asks to set up Varyz or the plugin reports that setup is required.

The source repository's marketplace root is its `plugins/` directory, which holds both marketplace catalogs. For local Claude Code testing, use `/plugin marketplace add <absolute checkout>/plugins` then `/plugin install varyz@varyz`. For Codex, run `codex plugin marketplace add "<absolute checkout>/plugins"`, then install Varyz from that marketplace in the desktop plugin UI. Adding the Git repository root alone will not discover these nested catalogs. Public marketplace/store publication remains a separate release step. Each client's package lives in `plugins/claude-code` or `plugins/codex`; local paths must be quoted when they contain spaces.

1. Tie setup to one outcome relevant to the user's task: retrieving earlier decisions, avoiding repeated background, or finding where work was left. Explain that local use requires no cloud account. Installation adds runtime dependencies, local models and a background service; the user chooses sources and agent connections. Excerpts retrieved locally may be sent to the connected AI host. Do not promote paid Cloud or use local setup to route to a purchase.
2. Find this installed plugin's `runtime/launcher.mjs` from its plugin root. It needs Node.js on PATH; report a missing runtime clearly instead of claiming setup succeeded.
3. Run `node <absolute plugin root>/runtime/launcher.mjs <claude-code|codex> --install --dry-run` using the client this plugin belongs to. Use argument arrays or proper quoting for paths with spaces. Prepared release ZIPs include an installer wheel inside each local plugin, so plugin-cache copies do not need the private repository. A source-marketplace checkout may still use repository source and require signed-in Git. Check the actual dry-run package path; do not assume a public PyPI package is available.
4. When the owner has asked to install, run the same command without `--dry-run`. This reuses the ordinary installer and opens its consent page. Let the owner choose agent connections and data sources. Never add `--yes`, connect all sources, or upload anything as a shortcut.
5. After setup, run `varyz sources` and `varyz hooks doctor`. Reconnect or restart the plugin so its bootstrap connection becomes the full local MCP service.
6. After confirming the plugin is installed, run `varyz plugin migrate --client <claude-code|codex> --config <the setup config> --dry-run`, then run it without `--dry-run`. This moves the existing approved credential to the OS credential store and removes only the redundant standalone MCP connection. It preserves global hooks and other servers. It never creates a grant. If migration fails, keep the existing working connection and report the error. Plugin hooks defer to existing Varyz global hooks per event.
7. Check which selected sources are ready; if their initial indexing is still running, report that instead of claiming history is available. Do not connect additional sources or broaden the selected folders. On an authorized local agent, use the user's current task to retrieve one useful result with local `recall` (read its schema first), or `varyz search` when the MCP needs restarting. Cite real source references and apply the finding to the task. If no relevant evidence is found, explain that and let the user continue without it or choose another source. Never fabricate a successful first result or save a proposed preference without confirmation.
8. Learning how the owner works is the last setup step, on by default. Call `start_task` with the user's task; its `background_job` is the setup step. Before going on, tell the owner in a short block what happens now, as the job words it: Varyz reads their past messages to AI agents in the background, on a smaller model through their own plan, to learn each project's aims, their taste, how they like work done and what they already decided; it skips anything sensitive and removes keys; rules with strong evidence take effect on trial and the rest wait in `varyz rules review`. Then start it as the job says (or say Varyz's own reader already started it). Do not ask permission first. Only if the owner says not now (in this conversation, before or after), ask once when (tonight, tomorrow morning, or a time they name), call `schedule_reading` with that time and confirm it in one line; Varyz keeps the time and reads then.
9. Cloud connection is a separate user-requested task, not part of onboarding. For an existing account, use `varyz cloud connect --url <owner-approved service URL>` and separate explicit record selection. Do not collect credentials in chat, initiate a subscription, or upload the raw archive. Hosted ChatGPT can use selected confirmed preferences; it cannot search this local archive.

Starting a normal session is never authorization to install, index sources, create an account or upload records.
